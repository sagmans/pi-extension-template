# Make documentation match the project

Follow [Start](../start.md). Identify the audience, task, and current source of truth. Read the target's behavior, commands, support evidence, contribution policy, and domain language before writing.

Document what the user needs to decide or do, not a prescribed set of files. Separate user usage from maintainer operations and private incident procedures. Establish terminology once; record durable rationale only when it explains a consequential choice.

For agent instructions, provide a compact operating map with conditional pointers to the relevant procedures. Derive commands from the target rather than inventing standard script names. Preserve instruction hierarchy and explain where the agent needs authorization. Use progressive disclosure instead of repeating every policy in every prompt.

Link [Pi's resources](../../resources/pi.md) for host behavior. Keep target-specific semantics, differences, prerequisites, and limits local. Distinguish declared support, verified behavior, and experimental features. Avoid copying a manual or presenting historical observations as current guarantees.

For contribution and review guidance, preserve the owner's policy. Describe how to report ordinary bugs, privately handle security findings, present change intent, and supply useful evidence. Issue forms and PR templates are optional target choices, not files to copy from this reference.

Verify links and example commands in the relevant disposable environment. Review a user's complete path from installation or discovery to the intended result. Report examples not exercised. Finish when the requested task is clear and consistent with behavior; do not add documentation scaffolding for hypothetical features.
